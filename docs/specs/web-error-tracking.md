# Spec: web error tracking

Module id: `web-error-tracking` · sixth of six (see [web.md](web.md)) · Depends on `web-errors` ·
Status: **done: merged 2026-11-08 (#53), released in v0.5.0; source-map upload stays open until a deployment exists (see web-error-tracking-todo.md)**

Facts below were checked in the repo on 2026-11-08.

## Objective

An error that breaks a screen in a user's browser reaches the team's GlitchTip with a readable stack
(source-mapped), the route, the release and an opaque user id, and with nothing a user typed. The
client is silent when no DSN is configured. Done means:

- a render crash, an unhandled rejection and a failed route load are reported once each;
- reported stacks point at the original TypeScript, not the minified bundle;
- an expected failure is never reported: a 401, a 4xx problem from the API, a validation error;
- no DSN, no network traffic from the SDK and no console noise.

## Status and the blocker

GlitchTip is decided (error tracking via the Sentry SDK, self-hosted, backend and frontend, enabled
by the DSN's presence) but **it is not in the repo**: no service in `docker-compose.yml`, no
`SENTRY_DSN` in `config/` or `.env.example`, nothing in `docs/`. The backend half is a separate
module that has no spec yet. This module needs two things from it: a GlitchTip to send to, and a
DSN setting. I will not build against a stub. Order: backend GlitchTip spec and PR first, then this.
If you would rather ship the frontend first against a GlitchTip you run by hand, say so.

## Decisions

1. **`@sentry/react`**, as decided. The SDK is initialised once in `main.tsx`; the router and
   `QueryClient` already surface errors in two places the plan hooks: the route error view
   (`web-errors`' `RouteError`) and `QueryCache`/`MutationCache` `onError`.
2. **Only unexpected errors.** An error is reported when it is not an API problem with a 4xx status
   and not a `GraphQLRequestError` whose code is a known client error; 5xx problems and network
   failures are reported. One function, `shouldReport(error)`, in `api/`, unit-tested.
3. **The DSN reaches the client at build time** (`VITE_SENTRY_DSN`), because the client is static.
   No toggle variable: the SDK starts only if the DSN is set, matching the rule for backend config.
4. **User context is the id only**: from the token's `sub`, never email or name. Request and
   response bodies, form values and URL query strings are never attached; `beforeSend` strips
   query strings and the `Authorization` header.
5. **Source maps** are generated by `make web-build` and uploaded to GlitchTip by the release step
   with the release name, then removed from `dist/` so they are not served. The release name is the
   same string the backend uses (the build's version).

## Testing

- Unit: `shouldReport` for a 404 problem, a 500 problem, a 401, a network `TypeError`, a
  `GraphQLRequestError` with `UNAUTHENTICATED` and one with `INTERNAL`; `beforeSend` removes a
  query string and the `Authorization` header.
- By hand against a real GlitchTip: throw in a component, see one event with a readable stack,
  route and user id; stop the API, see no event for the 401/4xx cases; unset the DSN, see no
  request to GlitchTip in the network panel.

## Boundaries

- Always: scrub in `beforeSend`; report each error once; keep the SDK out of the bundle's critical
  path where the DSN is absent (dynamic import).
- Ask first: each dependency; session replay or performance tracing (both off); tagging with
  anything beyond route, release and user id.
- Never: Sentry SaaS endpoints; the user's email; request bodies; source maps served from `dist/`.

## Success criteria

1. With a DSN: a thrown render error, an unhandled rejection and a 500 each produce one event with a
   source-mapped stack, the route, the release and the user id.
2. A 401, a 404 and a validation 422 produce no event.
3. Without a DSN: no SDK network request, no console output.
4. `dist/` contains no `.map` files; GlitchTip has the release's maps.
5. `make web-check` and `make web-build` pass.
